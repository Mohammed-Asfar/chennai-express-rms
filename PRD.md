# Chennai Express RMS — Product Requirements Document

**Version:** v1.0
**Date:** 2026-09-01
**Status:** Approved for build

---

## 1. Overview

Chennai Express RMS is a restaurant management and billing system for a single
restaurant, running on the billing counter PC. It handles table management, menu
setup, dine-in and takeaway orders, KOT printing to the kitchen, bill printing on
a thermal printer, and daily sales reporting.

The system is **local-first**: all billing works with no internet connection.
Data syncs to a cloud database in the background when a connection is available.

### 1.1 Goals

| # | Goal |
|---|---|
| G1 | Take a dine-in or takeaway order and print a correct bill in under 30 seconds |
| G2 | Never lose a sale — billing must work with no internet and no working printer |
| G3 | Run comfortably on a 4GB Windows PC |
| G4 | Support adding more branches later without migrating existing data |

### 1.2 Non-Goals (v1)

Online ordering, delivery/aggregator integration, inventory and stock, customer
loyalty, multi-branch UI, waiter mobile app, table merge/split, advance booking
beyond the current day.

Each is excluded from v1 scope only. The schema is designed not to block them.

## 3. Architecture

Flutter is a pure UI layer. The Node backend owns all data, business logic,
printing, and sync. There is no database or billing logic in the frontend.

```
┌────────────────────────────┐
│  Flutter Windows Desktop   │   UI only — no DB, no business logic
└─────────────┬──────────────┘
              │  HTTP (localhost)
┌─────────────▼──────────────┐
│    Node.js + Fastify       │   source of truth
│  ┌───────────────────────┐ │
│  │ SQLite (better-sqlite3)│ │
│  └───────────────────────┘ │
│  ┌───────────────────────┐ │
│  │ ESC/POS print service │─┼──► USB thermal printer
│  └───────────────────────┘ │──► LAN printer (TCP :9100)
│  ┌───────────────────────┐ │
│  │  Sync worker          │─┼──► Neon Postgres (cloud)
│  └───────────────────────┘ │
└────────────────────────────┘
```

### 3.1 Stack

| Layer | Technology | Reason |
|---|---|---|
| Frontend | Flutter (Windows desktop) | Native app window, ~90–150MB RAM total, fits 4GB target |
| Backend | Node.js 20+ / TypeScript / Fastify | Type safety for money math, built-in schema validation, low memory |
| Local DB | SQLite via `better-sqlite3` | Embedded, no install, ACID, synchronous queries keep billing logic readable |
| Cloud DB | Neon Postgres via `postgres` | Serverless, relational, branch-ready |
| Validation | Zod | Request validation at the API boundary |
| Auth | JWT + bcryptjs | Standard, no external dependency |
| Printing | ESC/POS over USB and TCP | Direct byte control, correct thermal output |
| Images | `jimp` | Pure JS — converts the branch logo to a 1-bit raster with no native build |

### 3.2 Rejected alternatives

| Considered | Rejected because |
|---|---|
| Electron frontend | 300–450MB RAM — unacceptable on a 4GB PC |
| Browser / kiosk mode | Staff need a real application, not a browser window |
| Local PostgreSQL | ~200MB idle RAM plus a server install on the restaurant PC |
| Drizzle ORM | Does not unify SQLite and Postgres schemas — separate `sqlite-core` and `pg-core` dialects, so its main draw here does not apply. Raw SQL migrations are clearer at this size and keep billing queries visible. |
| Prisma | One provider per schema file, so two files anyway; query engine process too heavy for the RAM target |
| Browser-side printing | Cannot reach USB; forces a print dialog per bill and poor thermal output |

## 4. Data Conventions

These are **non-negotiable** and apply to every table.

| Rule | Detail |
|---|---|
| **Money** | `INTEGER` **paise**, never float. ₹450.00 → `45000`. Display divides by 100. |
| **Primary keys** | `TEXT` UUID v4, generated by the backend. Never auto-increment — prevents branch↔cloud collisions. |
| **Timestamps** | UTC. SQLite `TEXT` ISO-8601; Postgres `TIMESTAMPTZ`. |
| **Booleans** | SQLite `INTEGER` 0/1; Postgres `BOOLEAN`. |
| **Multi-branch** | `branch_id` on every business table from day one. v1 always uses one branch and hides it in the UI. |
| **Sync** | Every synced table carries `updated_at` and `synced_at`. |
| **Soft delete** | `deleted_at` on transactional rows. Orders and bills are never hard-deleted. |
| **Naming** | `snake_case`, plural tables, `<singular>_id` foreign keys. |

**Why paise:** floating-point rounding silently produces wrong bills. Integer
arithmetic is exact. This is the single most important correctness rule in the system.

**Why UUIDs and `branch_id` now:** retrofitting either onto live billing data means
migrating real financial records. Both cost nothing today.

| `app_releases` | Published versions — cloud-only, read by the branch |

### 5.2 Three rules the requirements depend on

**Price lives on the variant, not the item.** Every menu item has at least one
variant; items without portions get one named `Standard`. So `order_items` always
references a `variant_id` — one code path, no special case.

**Order lines are snapshots.** `item_name`, `variant_name`, `unit_price`, and
`tax_rate` are copied onto the line when the item is added, never read live from the
menu. Renaming a dish, repricing it, or changing its tax rate must not alter an order
already placed or a bill already printed.

**Money and rates are integers.** Paise for money (₹450.00 → `45000`), basis points
for rates (5% → `500`). Never float — see `SCHEMA.md` §1.

`order_no` and `bill_no` are sequential per branch per **business day**, allocated by
the backend inside the insert transaction. Never generated by the frontend.

The business day is not the calendar day — a restaurant open past midnight keeps 1 AM
sales on the previous trading day, with the cutoff configured in settings.

### 6.3 Reservations

| ID | Requirement |
|---|---|
| FR-V1 | Staff can create a booking with customer name, phone, party size, and time |
| FR-V2 | A booking can hold **one or more tables** — a party of 12 across three tables is one booking |
| FR-V3 | Booked tables show as `reserved` on the floor screen |
| FR-V4 | Staff see today's bookings as a list |
| FR-V5 | On arrival, a booking converts to an order; the tables become `occupied` |
| FR-V6 | A booking can be marked `no_show` or `cancelled`, releasing its tables |
| FR-V7 | Reserving a table **warns but does not block** a walk-in order on it |
| FR-V8 | A booking can be edited or its table list changed while still `booked` |
| FR-V9 | Bookings are kept for reporting, never hard-deleted |
| FR-V10 | Booking a table that is already reserved for an overlapping time warns the staff member |
| FR-V11 | A booking still `booked` well past its time is highlighted so staff can chase or mark no-show |
| FR-V12 | Deleting a table removes it from any active booking, warning first |

**FR-V7 is deliberate.** Guests run late, bookings get cancelled by phone, and staff
will work around a system that refuses to seat a waiting customer. The warning
informs; it does not obstruct.

**Warnings are returned beside the saved record, never instead of it.** Creating a
booking, seating a walk-in on a booked table, and deleting a booked table all
succeed and return a `warnings` array. Nothing on this screen refuses an action a
staff member has decided on.

**A booking is filed on the trading day of its time, not the day it was taken.** A
booking entered at 11 PM for 1 AM belongs to the same trading day as the rest of
that night's service, under the branch's `business_day_start` cutoff.

**Seating creates the order inside the same transaction.** A booking that becomes
`seated` always has an order, and the order always has a booking pointing at it —
a crash between two separate calls could leave neither true.

**One booking becomes one order, on one table.** A party across three tables still
gets a single order and a single bill; `POST /reservations/:id/seat` takes the
table they actually sat at. v1 has no table merge. The tables not taken drop back
to `free` as soon as the booking stops being `booked`.

**Overdue is computed by the backend** (`isOverdue`, 20 minutes past the booked
time). A till left open overnight must not decide a booking is on time because its
own clock says so.

**Closing a booking keeps its table links.** `no_show` and `cancelled` are statuses,
not deletions — FR-V9 — and the tables free up because `reserved` counts only
tables held by a `booked` reservation.

**Day navigation, not a calendar.** The bookings screen steps a day at a time and
defaults to today. `reserved_at` is a full timestamp, so a booking can be taken for
any date the day bar reaches; there is no month view.

#### Tax calculation

Menu prices are either tax-inclusive or tax-exclusive, set per branch.

**All money is paise; all rates are basis points** (5% = `500`). Tax therefore divides
by **10000**, not 100. Getting this wrong overcharges by 100×.

**Order of operations — discount comes first, always:**

```
1. compute each line's gross/base from unit_price × qty
2. apply the discount, distributed proportionally across lines
3. compute tax on the DISCOUNTED amount
4. split each rate's tax into CGST and SGST
5. round off the total, if enabled
```

Tax must never be computed before the discount. A ₹10 discount on a ₹100 sale means
tax is owed on ₹90, not ₹100.

**Exclusive** — menu ₹100, GST 5%, customer pays ₹105:

```
line_base     = unit_price × qty
line_base_net = line_base − line_discount          ← discount first
line_tax      = round(line_base_net × rate / 10000)
line_total    = line_base_net + line_tax

subtotal      = Σ line_base
total         = Σ line_base_net + Σ line_tax
```

**Inclusive** — menu ₹100, GST 5%, customer pays ₹100, of which ₹4.76 is tax:

```
line_gross     = unit_price × qty
line_gross_net = line_gross − line_discount        ← discount first
line_base      = round(line_gross_net × 10000 / (10000 + rate))   ← extract backwards
line_tax       = line_gross_net − line_base        ← remainder, exact by construction
line_total     = line_gross_net

subtotal       = Σ line_base
total          = Σ line_gross_net
```

**CGST / SGST split — computed per rate group, not per line:**

```
for each distinct rate on the bill:
    group_tax = Σ line_tax for lines at that rate
    cgst      = group_tax / 2          ← integer division
    sgst      = group_tax − cgst       ← remainder
```

Splitting per line and summing is wrong. Three lines each taxed 7 paise give
`Σ round(7/2) = 12` for CGST against `21 − 12 = 9` for SGST — a 3 paise gap on a bill
where the two halves must differ by at most 1. Grouping first gives 10 and 11.

**Rules that prevent drift:**

- **Discount before tax.** Never tax an amount the customer is not paying.
- Round **once per line**, never on a running total.
- Derive the second half of a split by subtraction, never by rounding twice.
- In inclusive mode, `line_tax = gross_net − base` so the parts always sum to the
  price actually charged.
- Per-item rates mean a bill can carry several rates at once. Group tax lines by rate
  on the printout — GST rules require the rate breakdown to be visible.

**Distributing the discount across lines.** A bill-level discount must be split
proportionally, and the parts must sum back to the discount exactly. Assign
`round(discount × line_base / subtotal)` to each line, then give the **last line the
remainder** rather than its rounded share. Without that, a ₹100 discount across three
equal lines becomes ₹99.99.

**Discount cannot exceed the subtotal.** A discount larger than the bill would produce
a negative total; it is rejected at validation.

**FR-P17 matters in practice.** A table orders drinks, then food twenty minutes later.
Reprinting the whole ticket would make the kitchen cook the drinks again. Only the new
lines go out, which is what `order_items.kot_printed_at` tracks.

**On the logo:** thermal printers accept only 1-bit black-and-white rasters. A colour
or greyscale image must be converted — grayscale, resize to the paper width in dots
(576 for 80mm, 384 for 58mm), then dither. Doing this per bill would risk the 3-second
print target, so it is done once at upload and stored.

**FR-P9 is the most important requirement in this section.** A kitchen printer on
wifi will go offline. Losing the sale because of it is unacceptable.

| FR-A2 | Passwords are stored as bcrypt hashes, never plaintext |
| FR-A3 | Sessions use JWT |
| FR-A4 | Admin-only endpoints are enforced server-side |
| FR-A5 | Admin can create, edit, and deactivate users |
| FR-A6 | First run creates a default admin and forces a password change |

### 6.9 Restaurant Settings

| ID | Requirement |
|---|---|
| FR-C1 | Admin can edit restaurant name, address, phone, and GSTIN |
| FR-C2 | Admin can upload and replace a logo, and preview how it will print |
| FR-C3 | Admin sets `tax_mode` — inclusive or exclusive |
| FR-C4 | Admin sets the default GST rate, inherited by new menu items |
| FR-C5 | Admin sets the business-day cutoff hour |
| FR-C6 | Admin sets the bill number prefix and bill footer text |
| FR-C7 | Admin can enable round-off to the nearest rupee |
| FR-C8 | Changing `tax_mode` or a tax rate never alters existing bills |
| FR-C9 | Changing the business-day cutoff does not retroactively move already-billed orders to a different day |
| FR-C10 | Admin can back up and restore the local database from the UI |
| FR-C11 | Changing GSTIN or restaurant name affects future bills only — printed bills are historical records |

**FR-C8 restates the snapshot rule.** Settings changes apply to future orders only.

### 6.10 Sync

| ID | Requirement |
|---|---|
| FR-S1 | All writes go to SQLite first and succeed with no internet |
| FR-S2 | A background worker pushes rows where `synced_at IS NULL` to the cloud |
| FR-S3 | Rows are marked with `synced_at` on success |
| FR-S4 | **Sync never blocks billing** — it runs on a separate path and failure is invisible to the till |
| FR-S5 | Sync status (last success, pending count, quarantined count) is visible in the UI |
| FR-S6 | Sync is push-only while the till is in service — the branch is the source of truth |
| FR-S7 | Rows push in dependency order — a parent never arrives after its child |
| FR-S8 | Pushes are idempotent upserts — the same row twice does not duplicate |
| FR-S9 | Soft-deleted and voided rows sync too, so the cloud reflects cancellations |
| FR-S10 | Rows push in batches, never the whole backlog at once |
| FR-S11 | `print_jobs` never syncs — print state is meaningless in the cloud |
| FR-S12 | If the local database is lost, it is restored from the cloud at boot, before seeding |
| FR-S13 | Restore runs only into a completely empty database, never over existing data |
| FR-S14 | Restore is best-effort — no cloud, no network, or an empty cloud all fall through to normal first-run seeding |

#### Trigger

A fixed interval is wrong in both directions: wasteful when idle, laggy right after
a bill. Sync is event-driven with a safety net.

| ID | Trigger | Detail |
|---|---|---|
| FR-S12 | **On write** | Routes signal after committing; a ~2s debounce collapses a burst of edits into one push |
| FR-S13 | **Idle heartbeat** | If nothing has happened for 5 minutes, check anyway — catches rows missed by a crash mid-cycle |
| FR-S14 | **On reconnect** | Drain the backlog as soon as connectivity returns, rather than waiting for a tick |
| FR-S15 | **On startup** | Push whatever was pending when the process last stopped |

#### Failure handling

Sync fails in three genuinely different ways, and treating them alike is the mistake:
**transient** (no internet — nothing is wrong with the data), **persistent** (a
constraint violation, or a cloud migration that was never applied), and **poisonous**
(one bad row while everything behind it is fine).

| ID | Requirement |
|---|---|
| FR-S16 | Attempts 1–5 retry with exponential backoff: 30s, 1m, 2m, 4m, 8m |
| FR-S17 | After 5 failures a row is **quarantined** — skipped, so the queue keeps draining |
| FR-S18 | The attempt count and last error are stored on the row, for diagnosis without reading logs |
| FR-S19 | Quarantined rows surface in the UI with a count and a Retry action |
| FR-S20 | Retrying a quarantined row resets its attempt count |

**Backoff** stops a restaurant offline for a day from hammering a dead connection
thousands of times. **Quarantine** stops one malformed row from blocking today's
bills from reaching the cloud. **Surfacing** is the important one — silent failure
means the owner believes their cloud reports are complete when they are not.

### 6.11 Application Updates

| ID | Requirement |
|---|---|
| FR-U1 | The app knows its own version and build number, shown in Settings |
| FR-U2 | It checks the cloud for a newer release when the app opens, and whenever staff ask via "Check for updates" |
| FR-U3 | A newer release shows a dialog with the version and release notes |
| FR-U4 | The user chooses when to install — the app downloads the installer and launches it |
| FR-U5 | Download progress is visible and can be cancelled |
| FR-U6 | The installer's SHA-256 is verified before it is executed; a mismatch aborts the update |
| FR-U7 | An optional update can be dismissed, and is not shown again that day |
| FR-U8 | A release can be marked **mandatory**; its dialog cannot be dismissed |
| FR-U9 | A build below `min_supported_build` is forced to update before billing continues |
| FR-U10 | **An update check never blocks billing** — no network, no problem, the app works |
| FR-U11 | The update prompt does not appear while an order is open or a bill is being taken |
| FR-U12 | A failed download or install leaves the current version working and reports the reason |
| FR-U13 | Version comparison uses `build_number`, never a parsed version string |
| FR-U14 | A release can be withdrawn by deactivating it, without publishing a new build |

**FR-U10 and FR-U11 are the ones that matter operationally.** An update dialog
appearing mid-transaction, or a check that hangs because the internet is down, turns
a maintenance feature into a billing outage. The check is best-effort and silent on
failure.

**FR-U2 is startup-only, deliberately.** A till stays open all day, so a check on a
timer means a dialog can appear in the middle of service for someone who never asked
for it — and FR-U11 can only defer that, not prevent it. Opening the app is a moment
staff already expect to wait; mid-service is not. Anyone who wants an update sooner
has "Check for updates" in the user menu, which also ignores an earlier dismissal.

**FR-U9 exists for billing correctness.** After a tax or rounding fix, an old build
producing wrong bills must not keep running for months because staff kept dismissing
a dialog. Forcing is reserved for that class of fix — not for features.

**FR-U6 is a security requirement.** The app downloads a binary and executes it on
the billing PC. Without checksum verification, anyone who can intercept the download
runs code on that machine.

## 7. Edge Cases

Scenarios that occur in a working restaurant and their required behaviour.

### 7.1 Money and tax

| Scenario | Required behaviour |
|---|---|
| Discount applied to a bill | Tax computed on the **discounted** amount, never the original |
| Discount exceeds subtotal | Rejected at validation — a negative total is never produced |
| Bill-level discount across lines | Distributed proportionally; last line takes the remainder so parts sum exactly |
| Tax of an odd number of paise | CGST is `group_tax / 2`, SGST the remainder — halves differ by at most 1 |
| Items at different GST rates on one bill | Tax grouped and printed per rate |
| Round-off enabled | Applied once at the total, stored signed in `round_off` |
| Price changed mid-order | The line keeps its snapshot price; a re-add at the new price becomes a separate line |
| Zero-priced item (complimentary) | Allowed; contributes zero tax |
| Bill paid ₹500 cash + ₹300 card | Two payment rows; reports count each mode separately |
| Payment exceeding the bill total | Rejected — change is handled at the drawer, not recorded |
| Bill left unpaid | `payment_status` stays `unpaid`; the table still frees |
| GST switched off mid-day | Bills raised earlier keep their tax; ones raised after carry none |
| Inclusive mode with GST off | The "(Price includes GST)" note is dropped — it would claim a tax never charged |
| Unpaid bill printed for the table | Prints `*** UNPAID ***` with the total; the bill stays open for payment |
| Part-paid bill printed | Lists what was taken and prints `BALANCE DUE`, so the table can settle the rest |
| Bill settled after the billing dialog closed | Taken from the bill's detail in the bills list; status and takings both follow |
| Bill taken while another screen was open | The bills list and reports refetch when opened, so neither shows a stale figure |
| Amount edited above what is due | Refused by the backend with the outstanding figure, not silently clamped |
| Cash recorded when it was card | Reversed with a reason, correct payment added; the bill reopens for the amount |
| Void attempted on a paid bill | Refused — its payments must be reversed first, so the button is hidden until they are |
| Reason field holding only spaces | Rejected. Trimming happens before the length check, not after |
| Bill raised Monday, paid Wednesday | Sale reports on Monday, cash collection on Wednesday |
| Wrong payment mode recorded | Reversed with a reason, correct payment added; both rows stay |
| Voiding a bill that has payments | Blocked until the payments are reversed |

### 7.2 Orders and tables

| Scenario | Required behaviour |
|---|---|
| Two parties at one table | Two orders, two bills; table frees only when the last settles |
| Same item added twice | Merged into one line if `unit_price` matches, separate if not |
| All items removed from an order | Cannot be billed — must be cancelled |
| Order cancelled after KOT printed | Cancellation slip sent to the kitchen |
| Item removed after KOT printed | Order flagged so the kitchen can be told |
| Bill settled, then a mistake found | Admin voids the bill with a reason; order reopens for correction |
| Two terminals edit the same order | `version` column rejects the stale write rather than silently overwriting |
| Table deleted while a booking holds it | Removed from the booking, with a warning naming whose booking lost it |
| Order opened, nothing added, screen left | Discarded on the way out; the table frees itself |
| Table stranded seated by a crash | "Free this table" on its card discards the empty orders holding it |
| Walk-in seated on a booked table | Seated, with a warning naming the booking. Never refused |
| Booking whose every table was deleted | Refused at seating with an explanation, rather than failing on an empty list |
| Booking seated twice | The second attempt is refused; one booking never opens two orders |
| Cancelled booking on a table | Stops holding it and stops warning about it, but stays in the day's record |
| Booking edited after it was seated | Refused — it has become an order, and that is what changes now |

### 7.3 Printing

| Scenario | Required behaviour |
|---|---|
| Printer offline | Order and bill still save; job queues as failed with Retry |
| Slow USB printer via the Windows spooler | The result is polled, not read once after a fixed wait — a bill that printed must not report failure |
| Job left pending by a restart or an offline printer | A background sweep retries it, and the queue offers "Send now" rather than only waiting |
| No printer matches a job's role | Job queues as failed with a clear message — never silently dropped |
| Items added after a KOT already printed | Only the new lines print, marked as an additional KOT |
| Retry pressed on an already-printed job | Prevented — avoids duplicate KOTs reaching the kitchen |
| Cancel pressed on an already-printed job | Prevented — the paper is already out; recording it cancelled would be false |
| Job cancelled while a send is in flight | The send may not overwrite the cancellation; a job settles only while still pending |
| Cancel pressed twice | Second press succeeds quietly — a slow connection must not produce an error to interpret |
| Cancelled job and the retry sweep | Never picked up again; `drainPending` takes only pending jobs |
| Long item name on 58mm paper | Wraps or truncates cleanly; never garbled |
| Long restaurant name with the logo off | Wraps at the columns double-width leaves (24 on 80mm, 16 on 58mm), never off the paper |
| Tagline left empty | Nothing prints — no blank line pushing the bill down |
| Logo missing or corrupt | Bill prints without it |
| Bill reprinted | Prints exactly as the original; `reprint_count` records that it happened |

### 7.4 Time and reporting

| Scenario | Required behaviour |
|---|---|
| Sale at 1 AM | Belongs to the previous business day, per the configured cutoff |
| Business-day cutoff changed | Already-billed orders keep their original business date |
| Voided bill | Excluded from sales totals, but listable — void patterns are a loss signal |
| Discounts given | Reported separately with the user who applied them |

### 7.5 System

| Scenario | Required behaviour |
|---|---|
| Backend not running | UI shows a clear, actionable error, not a blank screen |
| Backend crashes mid-service | Auto-restarts; no committed order is lost |
| Power cut mid-bill | SQLite WAL means the last committed transaction survives |
| SQLite file deleted, disk replaced, or Windows reinstalled | Restored from the cloud at boot, before seeding, with its branch id intact |
| SQLite lost **and** no internet | Falls through to a normal first run; the cloud copy is restored on a later boot only if the database is still empty |
| SQLite lost after billing offline for days | Anything that never reached the cloud is not recoverable — restore returns the last pushed state |
| No internet for days | Billing unaffected; sync resumes when connectivity returns |
| Same row pushed to cloud twice | Idempotent — no duplicate created |
| A row repeatedly fails to sync | Surfaced in the UI rather than retried forever in silence |
| Update check with no internet | Fails silently; the app works normally |
| Update available while an order is open | The prompt waits until no order is in progress |
| Installer checksum does not match | Update aborts; the current version keeps running |
| A published release turns out to be broken | Deactivated in the cloud; clients stop being offered it |
| A build below the minimum supported version | Forced to update before billing continues |

### 7.6 Known limitations of v1

Accepted deliberately, listed so they are not mistaken for oversights:

| Limitation | Consequence |
|---|---|
| One bill per order | Splitting a bill between guests means creating separate orders up front |
| No table merge | A large party across three tables needs three orders, or one order on one table |
| Push-only sync | Menu edits made in the cloud do not reach the branch |
| Restore is automatic and unprompted | A fresh install pointed at a cloud database that already holds a branch inherits that branch's data instead of starting clean |
| Bookings step a day at a time | No month calendar; a distant date takes many taps |
| No inventory | Selling an item with no stock is not prevented |
| Updates are per-machine | Each billing PC updates itself; there is no central push |

### 9.1 Testing

Billing math has automated tests **from step 5, before any UI exists**. A wrong
total is the one defect that cannot ship.

Required coverage:

| Case | Why |
|---|---|
| Line totals and subtotal | Base arithmetic |
| Exclusive tax | Tax added on top |
| Inclusive tax extraction | Backwards derivation is the easiest thing to get wrong |
| Inclusive: `base + tax` equals the printed price exactly | The property that must never break |
| CGST + SGST equals total tax | Catches double-rounding |
| Odd-paisa tax split (e.g. tax of 7 paise) | The remainder rule |
| Mixed tax rates on one bill | Per-item rates, grouped output |
| Fixed and percentage discounts | Both paths |
| Discount distributed across lines | Proportional split must sum back to the discount exactly |
| **Tax computed after discount** | Taxing the pre-discount amount overcharges the customer |
| Discount exceeding subtotal | Must be rejected, never a negative total |
| Rate applied as basis points | `/10000` not `/100` — a 100× error |
| Round-off to nearest rupee | Applied once, stored signed |
| Zero-priced item | No division-by-zero, no tax |
| Bill number sequencing under concurrent inserts | No duplicates, no gaps |
| Void releases the order and excludes it from reports | Bill numbers are still consumed |
| Business-day boundary — a 1 AM sale | Belongs to the previous trading day |
| Split payment sums to the total | ₹500 + ₹300 settles an ₹800 bill exactly |
| Payment exceeding the total | Rejected |
| Partial payment leaves `payment_status = partial` | `amount_paid` matches the live payment rows |
| Reversed payment reduces `amount_paid` | Reversal is not counted |
| Void blocked while live payments exist | Money cannot sit against a voided sale |

## 10. Future Scope

Deliberately out of v1 but not blocked by the schema:

| Feature | What already supports it |
|---|---|
| Multiple branches | `branch_id` on every table; UUID keys prevent ID collisions |
| Waiter tablet app | Backend is already an HTTP API; Flutter targets Android from the same codebase |
| KOT routing by category | `printers` table exists; needs `printer_id` on `categories` |
| Table merge / split | Orders are separate from tables |
| Bluetooth printers | Print transport is an interface; add a third implementation |
| Add-ons / extras (extra cheese, extra gravy) | Would need an `order_item_addons` table; variants already separate item from priced option |
| Cloud admin dashboard | Neon already holds synced data |
| Inventory, loyalty, online orders | Not designed for; would need new tables |
