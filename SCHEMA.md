## 0. Source of Truth

**This document is the source of truth for the schema.** Migrations implement it;
this describes it. Both are hand-written and must change together.

```
        SCHEMA.md  ←──── source of truth, hand-maintained
            │
    ┌───────┴───────┐
    ▼               ▼
migrations/     migrations/
  sqlite/         postgres/
    │               │
    ▼               ▼
local SQLite    Neon cloud
```

### 0.1 Rules

| Rule | Detail |
|---|---|
| **`SCHEMA.md` changes in the same commit as the migration** | Never "later". A stale schema document is worse than none. |
| **Both dialects change together** | A SQLite migration without its Postgres counterpart breaks sync. |
| **Migrations are append-only** | Once applied to real data, a migration is immutable. Fix forward with a new one. |
| **Checksums verified at boot** | A modified applied migration is a hard startup error — this makes append-only enforceable rather than a convention. |

There is no code generator. The schema is small enough (17 tables) that generation
tooling would cost more than it saves. Keeping this document current is a review
responsibility — see `CLAUDE.md` §1.

### 0.2 Why migrations, not an ORM schema

An ORM schema file describes the *desired* state. The migration history describes
what *actually happened* to production data. For billing records that history is
the audit trail — it answers "when did this column change and what happened to the
existing rows". This is how most large engineering teams manage financial schemas.

### 0.3 Commands

```bash
pnpm db:migrate        # apply pending migrations to local SQLite
pnpm db:status         # show applied and pending local migrations
pnpm db:migrate:cloud  # apply pending migrations to Postgres / Neon
pnpm db:status:cloud   # show applied and pending cloud migrations
```

Both runners are append-only and verify checksums: a migration edited after it was
applied is a hard error, not a warning.

### 0.4 Type mapping

Every column type below maps to both dialects. This table **is** the mapping —
consult it when writing a migration.

| Logical type | SQLite | Postgres | Notes |
|---|---|---|---|
| `id` | `TEXT PRIMARY KEY` | `TEXT PRIMARY KEY` | UUID v4, backend-generated |
| `fk` | `TEXT REFERENCES x(id)` | `TEXT REFERENCES x(id)` | |
| `text` | `TEXT` | `TEXT` | |
| `money` | `INTEGER` | `BIGINT` | **paise** — never float |
| `int` | `INTEGER` | `INTEGER` | |
| `rate` | `INTEGER` | `INTEGER` | basis points — 5% = `500` |
| `bool` | `INTEGER` + `CHECK (x IN (0,1))` | `BOOLEAN` | |
| `timestamp` | `TEXT` ISO-8601 UTC | `TIMESTAMPTZ` | |
| `enum` | `TEXT` + `CHECK (x IN (...))` | `TEXT` + `CHECK (x IN (...))` | native `ENUM` avoided — additive changes stay cheap |
| `json` | `TEXT` | `JSONB` | |

**On `rate` as basis points:** tax rates are stored as integers, `500` = 5%, `250`
= 2.5%. Same reasoning as paise — a rate of `0.05` as a float reintroduces exactly
the drift that integer money avoids.

## 1. Conventions

| Rule | Detail |
|---|---|
| **Money** | Integer **paise**. ₹450.00 → `45000`. Never float, never decimal. |
| **Rates** | Integer **basis points**. 5% → `500`. |
| **Primary keys** | `TEXT` UUID v4, generated by the backend. Never auto-increment. |
| **Timestamps** | UTC always. SQLite ISO-8601 text; Postgres `TIMESTAMPTZ`. |
| **Multi-branch** | `branch_id` on every business table. v1 uses one branch, hidden in the UI. |
| **Sync** | `updated_at` and `synced_at` on every synced table. |
| **Soft delete** | `deleted_at` on transactional rows. Orders and bills are never hard-deleted. |
| **Naming** | `snake_case`, plural tables, `<singular>_id` foreign keys. |

### 1.1 Columns on every synced table

```sql
id          TEXT PRIMARY KEY,           -- UUID v4
branch_id   TEXT NOT NULL REFERENCES branches(id),
created_at  TEXT NOT NULL,              -- ISO-8601 UTC
updated_at  TEXT NOT NULL,              -- ISO-8601 UTC, bumped on every write
synced_at   TEXT,                       -- NULL = pending push to cloud
deleted_at  TEXT                        -- NULL = live (transactional tables only)
```

```
        ┌──────────┬───────────────┼───────────────┬──────────┐
        ▼          ▼               ▼               ▼          ▼
   ┌───────┐  ┌────────┐    ┌──────────┐    ┌────────┐  ┌────────┐
   │ users │  │sections│    │categories│    │printers│  │settings│
   └───────┘  └───┬────┘    └────┬─────┘    └───┬────┘  └────────┘
                  ▼              ▼              │
             ┌────────┐    ┌──────────┐         │
       ┌─────┤ tables │    │menu_items│         │
       ▼     └───┬────┘    └────┬─────┘         │
┌──────────────┐ │              ▼               │
│ reservation_ │ │   ┌──────────────────┐       │
│    tables    │ │   │menu_item_variants│       │
└──────┬───────┘ │   └────────┬─────────┘       │
       ▼         ▼            │                 │
┌──────────────┐ ┌────────┐   │                 │
│ reservations │►│ orders │   │                 │
└──────────────┘ └───┬────┘   │                 │
                     │        │                 │
            ┌────────┴────┐   │                 │
            ▼             ▼   │                 ▼
     ┌───────────┐   ┌───────┐│          ┌────────────┐
     │order_items│   │ bills │◄──────────┤ print_jobs │
     └───────────┘   └───┬───┘           └────────────┘
                         ▼
                   ┌──────────┐
                   │ payments │   ₹500 cash + ₹300 card = 2 rows
                   └──────────┘
```

Four relationships that are not one-to-one:

- A **section** holds many tables — AC, Non-AC, Terrace.
- A **reservation** holds many tables — a party of 12 across three tables is one
  booking — and points at the order created when the party is seated.
- A **table** may have several open orders at once — two parties sharing it — each
  with its own bill.
- A **bill** has many payments — split across cash, card, and UPI, and possibly
  taken on different days if the bill is left outstanding.

## 3. Tables

### 3.1 `branches`

The anchor. v1 has exactly one row.

| Column | Type | Notes |
|---|---|---|
| `id` | `id` | |
| `name` | `text` | "Chennai Express" |
| `address` | `text` | Printed on the bill |
| `phone` | `text` | |
| `gstin` | `text` | Nullable — unregistered restaurants have none |
| `logo` | `text` | Nullable — base64 PNG, uploaded by admin |
| `logo_bitmap` | `text` | Nullable — base64 1-bit ESC/POS raster, derived from `logo` |
| `logo_width` | `int` | Bitmap width in dots |
| `logo_height` | `int` | Bitmap height in dots |
| `print_logo` | `bool` | Admin can keep a logo on file but disable it on bills |
| `is_active` | `bool` | |

**Two logo columns, not one.** `logo` is the original the admin uploaded — shown in
the UI and kept so the bitmap can be regenerated. `logo_bitmap` is the monochrome
1-bit raster the thermal printer actually needs, converted once at upload rather
than on every bill.

Conversion (grayscale → resize to paper width → dither to 1-bit) is slow enough to
matter against the 3-second print target, and it depends on `printers.paper_width`:
576 dots for 80mm, 384 for 58mm. Regenerate the bitmap when the logo changes **or**
when a printer's paper width changes.

### 3.3 `sections`

Floor areas — AC, Non-AC, Terrace, Family Room.

| Column | Type | Notes |
|---|---|---|
| `id` | `id` | |
| `branch_id` | `fk` | |
| `name` | `text` | "AC", "Non-AC", "Terrace" |

| `is_active` | `bool` | |

```sql

```

Sections group tables on the floor screen and let reports break sales down by area.
A branch always has at least one; tables created before any section exists go to a
seeded `Main` section.

**No pricing or tax rules attached.** Historically Indian restaurants charged
different GST for AC and non-AC seating, but that distinction was removed in 2017 —
all restaurant service is now one rate. If a future rule reintroduces it, the
per-item `tax_rate` already exists and a section-level override could be added then.

### 3.4 `tables`

| Column | Type | Notes |
|---|---|---|
| `id` | `id` | |
| `branch_id` | `fk` | |
| `section_id` | `fk` | Which area the table sits in |
| `name` | `text` | "T1", "Terrace 3" |
| `seats` | `int` | |
| `status` | `enum` | `free`, `occupied`, `reserved` |
| `sort_order` | `int` | Display order on the floor screen |
| `is_active` | `bool` | |

```sql
UNIQUE (branch_id, name) WHERE deleted_at IS NULL
```

**`status` is derived state, maintained by the backend** — never set directly by the
client:

| Transition | Trigger |
|---|---|
| `free` → `occupied` | The **first** order opens on the table |
| `occupied` → `free` | The **last** open order settles or is cancelled |
| `free` → `reserved` | A reservation is created for it |
| `reserved` → `occupied` | A party arrives and an order opens |
| `reserved` → `free` | The reservation is cancelled or marked no-show |

`occupied` outranks `reserved`. A table with an open order shows occupied even if a
later booking exists for it.

**A table can hold several open orders at once** — two parties sharing a table each
get their own order and their own bill. So `occupied` means *at least one* open order
exists, and the table only returns to `free` when the last one closes.

**A bill left unpaid does not hold the table.** Billing closes the order, so the table
frees and can seat the next party; the outstanding balance follows the *bill*, not the
table. A guest who leaves owing money must not block seating.

```sql
-- correct: derive from open orders, never a bare UPDATE on settle
UPDATE tables SET status = CASE
  WHEN EXISTS (SELECT 1 FROM orders
               WHERE table_id = ? AND status = 'open' AND deleted_at IS NULL)
  THEN 'occupied' ELSE 'free' END
WHERE id = ?;
```

Setting `status = 'free'` directly when a bill settles would free a table that still
has another party seated at it.

### 3.6 `reservation_tables`

Join table — which tables a reservation holds.

| Column | Type | Notes |
|---|---|---|
| `reservation_id` | `fk` | |
| `table_id` | `fk` | |

```sql
PRIMARY KEY (reservation_id, table_id)
```

**Why a join table rather than `table_id` on `reservations`:** a large party booking
three tables must be one booking. Flagging three tables independently loses the fact
that they are one group — cancelling would mean finding and releasing three separate
records, and the guest list would show three parties instead of one.

**Enforcement is a warning, not a block.** A reserved table can still take a walk-in
order; the UI warns first. Guests run late, bookings get cancelled by phone, and staff
will work around a system that refuses to seat a waiting customer.

**`status` transitions:**

| From | To | Trigger |
|---|---|---|
| `booked` | `seated` | Party arrives, order opens, `order_id` set |
| `booked` | `no_show` | Marked by staff |
| `booked` | `cancelled` | Cancelled by staff |

Reaching `seated`, `no_show`, or `cancelled` releases every table on the booking back
to `free` — unless a table has an open order, in which case it stays `occupied`.

| `type` | `enum` | `dine_in`, `takeaway` |

**On `business_date`:** a restaurant open past midnight must keep 1 AM sales on the

### 3.11 `order_items`

Every priced field is a **snapshot** — copied at add time, never read live from the menu.

| Column | Type | Notes |
|---|---|---|
| `id` | `id` | |
| `order_id` | `fk` | |
| `variant_id` | `fk` | Reference only — never read for pricing |
| `item_name` | `text` | **Snapshot** |
| `variant_name` | `text` | **Snapshot** |
| `unit_price` | `money` | **Snapshot** — paise |
| `tax_rate` | `rate` | **Snapshot** — basis points |
| `qty` | `int` | > 0 |
| `line_base` | `money` | Taxable base after discount |
| `line_tax` | `money` | Tax on this line |
| `line_total` | `money` | What the customer pays for this line |
| `notes` | `text` | "no onion" — prints on the KOT |
| `kot_printed_at` | `timestamp` | NULL = not yet sent to kitchen |

**Why snapshots:** renaming a dish, repricing it, or changing its tax rate must never
alter an order already placed or a bill already printed. Reading `variant.price` at
billing time silently rewrites history. This is the most important rule in the schema.

**`kot_printed_at` drives incremental KOTs.** A table orders drinks, then food twenty
minutes later. Only lines with `kot_printed_at IS NULL` go on the next ticket —
reprinting the whole order would make the kitchen cook the drinks twice.

**Merging repeat adds.** Adding the same variant again increments `qty` on the
existing line rather than creating a duplicate — but only if `unit_price` matches. If
the price changed between the two adds, they must stay separate lines, because the
snapshot rule means each carries its own price.

### 3.12 `bills`

| Column | Type | Notes |
|---|---|---|
| `id` | `id` | |
| `branch_id` | `fk` | |
| `order_id` | `fk` | **One bill per order** — unique |
| `bill_no` | `int` | Sequential per branch per day |
| `business_date` | `text` | Matches the order |
| `subtotal` | `money` | Σ `line_base` |
| `discount_type` | `enum` | `none`, `fixed`, `percent` |
| `discount_value` | `int` | Paise if fixed, basis points if percent |
| `discount_amount` | `money` | Resolved paise actually deducted |
| `cgst` | `money` | |
| `sgst` | `money` | |
| `round_off` | `money` | Signed — may be negative |
| `total` | `money` | Final payable |
| `amount_paid` | `money` | Σ of its `payments` rows — maintained by the backend |
| `payment_status` | `enum` | `unpaid`, `partial`, `paid` — derived from `amount_paid` vs `total` |
| `tax_mode` | `enum` | **Snapshot** — `inclusive`, `exclusive` |
| `tax_breakdown` | `json` | Per-rate CGST/SGST split for the printout |
| `settled_at` | `timestamp` | Set when `payment_status` reaches `paid`. NULL while outstanding. |
| `customer_name` | `text` | Nullable — who owes, when a bill is left unpaid |
| `customer_phone` | `text` | Nullable |
| `void_reason` | `text` | Required when voided |
| `voided_at` | `timestamp` | NULL = live |
| `voided_by` | `fk` | `users.id` — admin only |
| `reprint_count` | `int` | Incremented on each reprint |
| `created_by` | `fk` | |

```sql
UNIQUE (branch_id, business_date, bill_no)
UNIQUE (order_id) WHERE deleted_at IS NULL
```

**One bill per order.** Two parties sharing a table are two orders and therefore two
bills — splitting happens at the order, never at the bill. This keeps every bill a
complete, self-contained record of one order.

**Voiding, not deleting.** A wrong bill is voided with a reason and an admin's user
id; the row stays. Voiding releases its order back to `open` so it can be corrected
and re-billed. Reports exclude voided bills but can list them — a pattern of voids is
a loss signal worth seeing.

**`reprint_count` exists so reprints can be marked as duplicates.** A reprinted bill
that looks identical to the original is a way to present one sale as two.

**The bill number is still consumed by a voided bill.** Numbering never reuses a gap;
an auditor seeing bill 42 missing with 41 and 43 present is a worse outcome than
seeing 42 marked void.

**`tax_breakdown` shape** — GST requires the rate-wise split visible when a bill
carries more than one rate:

```json
[
  { "rate": 500,  "base": 120000, "cgst": 3000, "sgst": 3000 },
  { "rate": 1800, "base": 20000,  "cgst": 1800, "sgst": 1800 }
]
```

**`tax_mode` is snapshotted** for the same reason prices are — a branch switching from
inclusive to exclusive must not change what last month's bills mean.

**`amount_paid` and `payment_status` are derived, never set directly.** Both are
recalculated from the bill's `payments` rows inside the same transaction as any
payment insert or reversal:

```sql
amount_paid    = Σ payments.amount WHERE reversed_at IS NULL
payment_status = 'paid'    when amount_paid >= total
                 'partial' when amount_paid >  0
                 'unpaid'  when amount_paid =  0
```

They are stored rather than computed on read so the outstanding-bills list and the
day's reports do not aggregate the payments table on every query.

### 3.13 `payments`

A bill has **many payments** — ₹500 cash plus ₹300 card is two rows.

| Column | Type | Notes |
|---|---|---|
| `id` | `id` | |
| `branch_id` | `fk` | |
| `bill_id` | `fk` | |
| `mode` | `enum` | `cash`, `card`, `upi` |
| `amount` | `money` | Paise. Must be > 0. |
| `reference` | `text` | Nullable — UPI txn id, card auth code |
| `paid_at` | `timestamp` | When this payment was taken |
| `business_date` | `text` | Trading day the payment was **received** |
| `reversed_at` | `timestamp` | NULL = live. A wrong payment is reversed, never deleted. |
| `reversed_by` | `fk` | `users.id` |
| `reverse_reason` | `text` | Required when reversed |
| `created_by` | `fk` | Who took the payment |

**Why its own `business_date`.** A bill raised on Monday and settled on Wednesday has
its sale on Monday and its cash on Wednesday. Sales reports use `bills.business_date`;
cash-collection reports use `payments.business_date`. Conflating them makes the cash
drawer disagree with the sales figure.

**Payments are reversed, not deleted.** A cashier recording ₹500 cash when it was card
reverses the row and adds a correct one. Both stay for audit.

**Overpayment is rejected.** `Σ amount` may not exceed `bills.total`. Change given on
a cash payment is handled at the drawer, not recorded as a negative payment.

**A voided bill's payments are reversed first.** Voiding a bill that still has live
payments would leave money recorded against a sale that no longer exists.

### 3.17 `app_releases`

**Cloud-only.** Lives in Neon, never in branch SQLite — a branch cannot tell itself

| Column | Type | Notes |
|---|---|---|
| `id` | `id` | |
| `version` | `text` | Semantic version, e.g. `1.2.0` |
| `build_number` | `int` | Monotonic. **This is what version comparison uses.** |
| `channel` | `enum` | `stable`, `beta` |
| `download_url` | `text` | Installer location |
| `file_size` | `int` | Bytes — lets the UI show progress |
| `sha256` | `text` | Checksum of the installer |
| `release_notes` | `text` | Shown in the update dialog |
| `is_mandatory` | `bool` | The dialog cannot be dismissed |
| `min_supported_build` | `int` | Builds below this are forced to update |
| `released_at` | `timestamp` | |
| `is_active` | `bool` | Unset to pull a bad release without deleting it |

**Comparison uses `build_number`, not `version`.** Parsing and comparing semantic
version strings correctly is fiddly and easy to get subtly wrong; a monotonic integer
cannot be ambiguous. `version` is for humans.

**`sha256` is not optional.** The app downloads an installer and executes it. Running
an unverified binary on the billing PC is the worst outcome in this system, so a
checksum mismatch aborts the update.

**`min_supported_build` handles the case that matters:** a release that fixes billing
math. An old build producing wrong bills must not keep running for months because
staff dismissed a dialog.

**`is_active` is the rollback.** A release that turns out to be broken is deactivated
in one row, and clients stop being offered it — no need to publish another build.

## 5. Sync

| Table | Synced to cloud |
|---|---|
| `branches`, `users`, `sections`, `tables`, `categories`, `menu_items`, `menu_item_variants` | Yes |
| `reservations`, `reservation_tables` | Yes |
| `orders`, `order_items`, `bills`, `payments` | Yes |
| `settings` | Yes |
| `print_jobs` | **No — branch-local** |
| `app_releases` | **No — cloud-only**, read by the branch, never written by it |

**Push-only in v1.** The branch is the source of truth; the cloud is a read replica
for reporting. Nothing flows back down, so there is no "the cloud changed this too"
case to reconcile — that is the single biggest simplification in the design, and why
v1 needs no conflict resolution.

### 5.1 Mechanism

Rows with `synced_at IS NULL` are pushed in batches, in dependency order, and
stamped on success. Sync runs on a separate path from billing and its failure is
invisible to the till.

**Push order** — a child must never arrive before its parent, or the foreign key
rejects it:

```
branches → users → sections → tables → categories → menu_items
         → menu_item_variants → reservations → reservation_tables
         → orders → order_items → bills → payments → settings
```

**Every push is an idempotent upsert:**

```sql
INSERT INTO orders (...) VALUES (...)
ON CONFLICT (id) DO UPDATE SET ...
```

If the connection dies after Postgres commits but before SQLite records `synced_at`,
the next cycle pushes the row again. A plain `INSERT` would fail on the duplicate
key. UUID primary keys make the re-push harmless — the same row always carries the
same id, so it overwrites itself.

**Deletions sync like any other change.** A cancelled order sets `deleted_at` and
clears `synced_at`, so the row pushes again carrying its deletion. The cloud records
the cancellation rather than the row silently vanishing.

### 5.2 Sync columns

Beyond `synced_at`, every synced table carries:

| Column | Type | Notes |
|---|---|---|
| `sync_attempts` | `int` | Consecutive failures. Reset to 0 on success or manual retry. |
| `sync_error` | `text` | Last failure message, for diagnosis without reading logs |

A row with `sync_attempts >= 5` is **quarantined**: skipped by the worker so it
cannot block the rows behind it, and surfaced in the UI with a Retry action.

**Why quarantine rather than retry forever:** one malformed row must not stop today's
bills reaching the cloud. **Why surface it:** silent failure means the owner believes
their cloud reports are complete when they are not.

### 5.3 Triggers

| Trigger | Timing |
|---|---|
| After a write | ~2s debounce, so a burst of order edits becomes one push |
| Idle heartbeat | Every 5 minutes — catches rows missed by a crash mid-cycle |
| On reconnect | Immediately, rather than waiting for the next tick |
| On startup | Whatever was pending when the process last stopped |

Backoff between retries is 30s, 1m, 2m, 4m, 8m. A restaurant offline for a day must
not hammer a dead connection thousands of times.

## 6. Numbering

`order_no` and `bill_no` are sequential **per branch per business day**, allocated by
the backend inside the same transaction as the insert:

```sql
SELECT COALESCE(MAX(bill_no), 0) + 1 FROM bills
WHERE branch_id = ? AND business_date = ?;
```

Because `better-sqlite3` is synchronous and SQLite serialises writers, this cannot
produce a duplicate. The `UNIQUE (branch_id, business_date, bill_no)` constraint is
the backstop.

**Never generated client-side.** Two terminals would allocate the same number.

## 7. Migrations

```
db/
  migrations/
    sqlite/
      0001_init.sql
      0002_add_variants.sql
    postgres/
      0001_init.sql        ← same number, same change, other dialect
      0002_add_variants.sql
```

Matching numbers in both folders describe the same change. A migration present in
one folder and missing from the other is a bug — sync will fail on the first row
that uses the new column.

| Rule | Detail |
|---|---|
| Numbered sequentially | `0001`, `0002` — order is the history |
| Append-only once applied | Never edit a migration that has run on real data. Fix forward. |
| Applied in a transaction | A failed migration leaves no partial state |
| Tracked in `_migrations` | `(version, applied_at, checksum)` |
| Checksum verified on boot | A changed applied migration is a hard startup error |

The checksum check is what makes append-only enforceable rather than a convention.
